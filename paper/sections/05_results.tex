\section{RESULTS}\label{sec:results}

All measured values in this section come straight from the campaign's raw telemetry
(Section~\ref{sec:method}), and each can be traced to the script that computed it. The only numbers
typed by hand are design constants and figures quoted from the base paper. All \NRunsTotal{} runs
across the three arms completed; none aborted and none hit the token ceiling. The provenance check
flagged $\NProvenanceProblems{}$ deviation across the merged arms. Midway through the campaign the
supervisor had to be restarted after a host infrastructure failure that had nothing to do with the
experiment. The fix shipped with that restart touched only the supervisor's health check and no code
that a run executes, and we confirmed this with a diff before treating the three arms as one dataset.
The first three subsections answer RQ1--RQ3 with the live model. Section~\ref{sec:livemock} then shows
that those answers change depending on whether the model was real (RQ4).

Table~\ref{tab:main} reports medians and interquartile ranges per configuration, and
Table~\ref{tab:effects} compares each configuration with \texttt{baseline} using bootstrap confidence
intervals, Cliff's $\delta$, and Holm-corrected Mann--Whitney $p$-values.
Figures~\ref{fig:mttr} and~\ref{fig:effects} show the underlying distributions and effect sizes. The
\texttt{full} configuration changes MTTR from \NMttrBaselineMedian{}\,s to \NMttrFullMedian{}\,s
($\Delta=\NDiffMttrSFull{}$\,s, $\NRelpctMttrSFull{}$\%, Cliff's $\delta=\NDeltaMttrSFull{}$,
$p_{\mathrm{Holm}}\NPHolmMttrSFull{}$) and cost from \NCostBaselineMedian{} to \NCostFullMedian{}
units ($\NRelpctCostUnitsFull{}$\%, $\delta=\NDeltaCostUnitsFull{}$,
$p_{\mathrm{Holm}}\NPHolmCostUnitsFull{}$). Both effects are significant, but the MTTR reduction is far
smaller than the one the mock evaluation of the same configuration produces
(Section~\ref{sec:livemock}).

Cost is the only headline metric whose change reaches the base paper's reported 25\% reduction, but
the reduction depends on the assumed provisioning gap (Section~\ref{sec:sensitivity}). Most of it
comes from the provisioning term of Eq.~\eqref{eq:cost}, which is an assumption, rather than from
metered compute. The pooled figure also hides two features of the cost data. First, the saving
depends on the scenario: the median cost of \texttt{full} is below that of \texttt{baseline} in three
scenarios but above it in \texttt{ingress\_burst} (\NCostScenFullIngressBurst{} against
\NCostScenBaselineIngressBurst{} units). Second, agent configurations that do not right-size cost far
more than \texttt{baseline} in the pooled data: \texttt{monitor\_only} and \texttt{recovery\_only} by
\NRelpctCostUnitsMonitorOnly{}\% and \NRelpctCostUnitsRecoveryOnly{}\%, and \texttt{schema\_only} by
\NRelpctCostUnitsSchemaOnly{}\%. Because these configurations hold the same static allocation as
\texttt{baseline}, the excess lies entirely in the metered compute term, and it is largely an
artifact of how that term is measured (Section~\ref{sec:limitations}). Resources are sampled once
before injection and once after the settle, so an agent configuration meters compute over its full
300\,s loop, whereas a non-agent configuration, whose response completes without waiting, meters only
a few seconds. The saving is therefore better attributed to the right-sizing configurations, chiefly
the optimization agent, than to agent control in general.

Manual interventions move in the opposite direction. The median rises from \NIntervBaselineMedian{}
to \NIntervFullMedian{} ($\Delta=\NDiffManualInterventionsFull{}$,
$\NRelpctManualInterventionsFull{}$\%, $\delta=\NDeltaManualInterventionsFull{}$,
$p_{\mathrm{Holm}}\NPHolmManualInterventionsFull{}$), the reverse of the base paper's reported
reduction of more than 70\%, and \texttt{recovery\_only} shows the same rise
($\NRelpctManualInterventionsRecoveryOnly{}$\%). One plausible mechanism is that \texttt{baseline}
escalates exactly once per injected fault by construction, whereas an agent configuration that is
rate-limited or denied by the budget can propose again on a later tick of the same 300\,s loop, with
each cycle adding an escalation. We did not instrument which mechanism dominates, so we report the
measurement and leave the mechanism open (Section~\ref{sec:discussion}). Because reducing manual
interventions is the system's stated purpose, we count this increase as a negative result for the
design. The answer to RQ1 is therefore mixed: with a live model, the full system beats static
orchestration on recovery time and cost, but not on manual interventions.

\subsection{Is the Full System Better Than Cheap, Non-Agent Automation?}

The \texttt{rule\_based} and \texttt{autoscale} configurations call no model, yet both beat every
agent configuration on MTTR, including \texttt{full}. That ranking follows from the remediation
latencies we modelled in Section~\ref{sec:method}. Each comparator resolves a covered fault after a
fixed 30\,s or 20\,s, so its numbers show what an idealized non-LLM responder could do, not how fast a
deployed one actually is. \texttt{rule\_based} reaches \NMttrRuleBasedMedian{}\,s
($\NRelpctMttrSRuleBased{}$\% relative to \texttt{baseline}, $\delta=\NDeltaMttrSRuleBased{}$), and
\texttt{autoscale} reaches \NMttrAutoscaleMedian{}\,s ($\NRelpctMttrSAutoscale{}$\%,
$\delta=\NDeltaMttrSAutoscale{}$), compared with $\NRelpctMttrSFull{}$\% for \texttt{full}. Neither
raises manual interventions (\mbox{\NRelpctManualInterventionsRuleBased{}\%} and
\mbox{\NRelpctManualInterventionsAutoscale{}\%}), while \texttt{full} raises them.

On cost, \texttt{autoscale} moves the median by \NRelpctCostUnitsAutoscale{}\%, less than the
\NRelpctCostUnitsFull{}\% achieved by \texttt{full}. \texttt{rule\_based}, which does not
right-size, shows no cost effect ($\NRelpctCostUnitsRuleBased{}$\%,
$p_{\mathrm{Holm}}=\NPHolmCostUnitsRuleBased{}$), as its design predicts. By construction, neither
comparator can execute an accepted mitigation (\texttt{decision\_correct}$=0$), and decision quality is
the one axis on which \texttt{full} wins outright (Section~\ref{sec:decision}). For these fault
scenarios and this control-loop timing, cheap deterministic automation beats the LLM-driven system on
two of the four metrics. For idealized comparators, then, the answer to RQ2 is negative: the agent
system does not beat cheap automation on speed or on manual interventions.

\subsection{Decision Quality}\label{sec:decision}

The \texttt{decision\_correct} metric is scored against a per-scenario set of accepted mitigations
(Eq.~\ref{eq:decision}, Section~\ref{sec:method}), and every non-agent configuration scores zero by
construction. Among the agent configurations, only \texttt{full}
($\delta=\NDeltaDecisionCorrectFull{}$, $p_{\mathrm{Holm}}\NPHolmDecisionCorrectFull{}$),
\texttt{optimization\_only} ($\delta=\NDeltaDecisionCorrectOptimizationOnly{}$), and
\texttt{schema\_only} ($\delta=\NDeltaDecisionCorrectSchemaOnly{}$) change the metric significantly;
\texttt{monitor\_only} and \texttt{recovery\_only} do not. Against an all-zero comparator, Cliff's
$\delta$ equals the treatment group's success rate, so these values are also correct-mitigation
rates: \texttt{full} executes an accepted mitigation in $\NDeltaDecisionCorrectFull{}$ of its runs.
This is the one metric on which the live system achieves something that neither the static baseline
nor the rule-based comparator can achieve at all. It answers RQ3 only in part, however, because fewer
than half of the full system's runs act correctly. As Section~\ref{sec:livemock} shows, the mock
evaluation scores the same configuration at \NLiveVsMockDecisionCorrectMock{}.

Table~\ref{tab:scenarios} and Fig.~\ref{fig:scenarios} break MTTR down by configuration and
scenario. No single configuration dominates every fault type. \texttt{optimization\_only} is the
fastest configuration on \texttt{ingress\_burst} but is slower than \texttt{baseline} on
\texttt{schema\_drift}, a fault on which its only non-monitoring agent has no lever, and
\texttt{schema\_only} shows the mirror-image pattern. This is the pattern a single-agent ablation
should produce: the agent helps where it owns the fault and is inert, or pure overhead, elsewhere. It
also cautions against treating any single scenario's result as a configuration's typical behavior.

Table~\ref{tab:live_mock} and Fig.~\ref{fig:live_mock} compare \texttt{full} under two conditions
that differ only in the model: arm A (live) and arm C, its deterministic-mock counterpart. MTTR is
\NLiveVsMockMttrSLive{}\,s with the live model and \NLiveVsMockMttrSMock{}\,s with the mock, a
divergence ratio of $R_{\mathrm{MTTR}}=\NLiveVsMockMttrSRatio{}$ (Eq.~\ref{eq:ratio}). The median
decision-correct score goes from \NLiveVsMockDecisionCorrectLive{} live to
\NLiveVsMockDecisionCorrectMock{} mock, even though the live correct-mitigation rate is
\NDeltaDecisionCorrectFull{}. Manual interventions drop from \NLiveVsMockManualInterventionsLive{} to
\NLiveVsMockManualInterventionsMock{}. Freshness drops from \NLiveVsMockFreshnessSLive{}\,s to
\NLiveVsMockFreshnessSMock{}\,s.

Cost goes the opposite way. The live arm costs less than the mock arm (\NLiveVsMockCostUnitsLive{}
vs.\ \NLiveVsMockCostUnitsMock{} units), and the mock even costs more than \texttt{baseline}. We think
most of this gap comes from the harness, not the model. The campaign never reset two global settings
between runs, the Airflow pool size and the streaming-worker target, so every run started from
whatever the previous agent action had left behind. The mock arm ran last, right after
\texttt{schema\_only}. In schema drift and upstream delay, the mock's rule-based optimization agent
does nothing, and mock \texttt{full} meters exactly the compute that live \texttt{schema\_only} did.
Live \texttt{full} ran first, from another starting state, and its metered compute stayed low in three
of the four scenarios. The cost difference between the two arms therefore does not cleanly measure
what the model changes, and we do not read it that way.

These results answer RQ4. The mock evaluation is not a noisier or scaled-down version of the live
one. On recovery time and decision quality it is a categorically different and far more flattering
experiment, and the earlier results in this section should be read with that in mind. We cannot tell
which evaluation path produced the base paper's headline figures, because the paper does not say.
What this campaign does show, for one system, is how much the evaluation path by itself can shift the
result. A claim
about this class of system drawn from a mock run is a claim about the mock, not about the model it
replaces.

\subsection{LLM Accounting}

\begin{table*}[t]
\centering
\caption{Model Usage per Agent Configuration, Counted Where Each Call Is Made or Skipped}
\label{tab:llm}
\small
\input{generated/tab_llm.tex}

Table~\ref{tab:llm} reports real model calls, cache hits, degraded proposals, invalid outputs,
tokens, and latency for each agent configuration, counted at the moment a call is or is not made
(Section~\ref{sec:method}). Over the whole campaign, the degraded and invalid rates are both zero. No
run used up its budget or ran into a provider outage, and no output that failed the schema made it
into the final runs. That holds for \emph{this} campaign and is not guaranteed in general. In the
pilot that came before it we found a live cache-poisoning defect, which is precisely what the
accounting is meant to catch, and we fixed it before the campaign started.

In absolute terms, the agents cost little. Across the \NRunsLive{} live-arm runs, the agents
made \NLlmCallsTotal{} real model calls and consumed \NApiTokensTotal{} API tokens in total, and no run
came close to the per-run budget: the largest used \NApiTokensMaxRun{} tokens against a cap of
\NBudgetTokens{}, and at most \NLlmCallsMaxRun{} calls against a cap of \NBudgetCalls{}. The per-run
model latency in Table~\ref{tab:llm} is small compared with the 300\,s control loop, so inference time
alone does not explain the live system's recovery time. We do not convert tokens into a monetary
cost, because the provider's per-token prices were not recorded with the runs; token counts are the
portable measure.

Table~\ref{tab:sensitivity} and Figs.~\ref{fig:human_sensitivity} and~\ref{fig:cost} present the two
closed-form sensitivity analyses of Section~\ref{sec:method}. \texttt{full} continues to beat the
simulated human down to a median human latency of \NBreakEvenHumanFull{}\,s, well below the assumed

static provisioning level of \NBreakEvenStaticFull{} units; below that level, a baseline that was
never heavily over-provisioned removes the saving on its own. Both analyses make the point of
Section~\ref{sec:livemock} from another angle: the headline numbers depend on modeling choices, so we
report each number together with the condition it depends on.

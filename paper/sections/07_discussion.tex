\section{DISCUSSION}\label{sec:discussion}

\subsection{Implications for Evaluating Governed Agents}
Taken together with the lessons of Section~\ref{sec:lessons}, the difference between mock and live
runs (Section~\ref{sec:livemock}) suggests four practices for evaluating governed-agent systems. The
first is to state whether the model in the loop was real or mocked and, where both numbers are
available, to report both, since a figure obtained with a mock mainly characterizes the mock. The
second is to include inexpensive non-LLM baselines. Here, two idealized ones beat the full agent system on recovery time and manual
interventions, and a comparison with static orchestration alone would have hidden that. Third, grade
safety claims against an oracle that shares no code with the mechanism being tested. Ours found two
contract-layer gaps that the system's own tests had missed. Fourth, before a long campaign, pay for a
short pilot at the real settings. Ours hit a retired model on its very first call.

\subsection{Deployment Implications}
For deployment, the most relevant decision-quality figure is $\NDeltaDecisionCorrectFull{}$
(Table~\ref{tab:effects}), not the
headline MTTR: at these settings \texttt{full} executes an accepted mitigation in fewer than half of
its runs. Together with the rise in manual interventions, this campaign gives no support for running
this class of system unattended and fully autonomously against real infrastructure. The results
instead favor the graduated trust ladder of Section~\ref{sec:system} as the safer production
default: shadow, approval, and autonomous modes, with a durable kill switch and a per-target action
cap. Nor do we think the full autonomy used as the research benchmark's default should be read as a
recommendation for deployment. For now, the trust core is an architectural response to a question that
our measurements raise; we have not yet measured whether it works.

\subsection{The Manual-Intervention Mechanism Is Measured, Not Explained}
Section~\ref{sec:results} shows that \texttt{full} and \texttt{recovery\_only} raise manual
interventions compared with \texttt{baseline}, which contradicts the base paper. The measurement is
straightforward: the metric counts rows in the
\texttt{telemetry.\allowbreak manual\_\allowbreak interventions} table, and every configuration writes
to that table. Why the count rises is a separate question, and we have not answered it. Possible explanations include a fault that remains open and is escalated again on successive ticks,
and repeated denials that eventually end in a hand-off to the human, and the two may well occur
together. Separating them would require a per-tick trace of proposal outcomes over the lifetime of a
fault, which the current telemetry does not record. Section~\ref{sec:humanartifact} does settle part
of the question: the median human-resolved \texttt{full} run escalated \NHumanEscalationsFull{} times
(Table~\ref{tab:humancheck}), so repeated escalation on an open fault contributes at least some of
the increase. Beyond that we leave the mechanism open rather than infer it from the totals. Readers should not
assume it resolves in the
system's favor.

\subsection{Limitations and Threats to Validity}\label{sec:limitations}

\subsubsection{Threats to Validity}
We see nine threats. \emph{Simulated human.} All comparisons with \texttt{baseline} depend on the
log-normal on-call model. Section~\ref{sec:sensitivity} gives the break-even point; it does not argue
that the model is right. \emph{Per-escalation human draws.} The simulator drew one delay per
escalation and kept the fastest, so configurations that escalate repeatedly get shorter MTTRs.
Section~\ref{sec:humanartifact} attributes most of the MTTR gain of \texttt{full} and
\texttt{recovery\_only} to this effect. \emph{Modelled baselines.} In \texttt{rule\_based} and \texttt{autoscale},
covered faults are resolved after fixed latencies that we assumed (Section~\ref{sec:method}). Their
lead over the agents comes from those assumptions and is not a measurement of any deployed rule engine
or autoscaler. \emph{Synthetic workload.} Our data are a downscaled synthetic table with injected
faults, not production traces, and real workloads may behave differently. \emph{One live model
family.} The live arm used one reasoning model and one faster model
from a single provider at temperature zero, so the decision-quality findings
(Section~\ref{sec:results}) are properties of that pairing and may not generalize. \emph{Unequal
replicate counts.} \texttt{baseline}, \texttt{rule\_based}, \texttt{autoscale}, and \texttt{full} each
have $\NNFull{}$ runs, whereas the four single-agent ablations have half as many. We made this
trade-off for cost reasons before the campaign started (Section~\ref{sec:method}), and it leaves the
ablations with wider confidence intervals than the headline comparisons. \emph{Nominal seed matching.} Because the per-run
seed depends on the configuration name (Section~\ref{sec:method}), no two configurations share fault
or human-latency randomness at a matched (scenario, replicate) index. We therefore used the unpaired
rank-sum test as the primary test, and the retained signed-rank statistic should not be read as
evidence from a paired design. \emph{Detection-clock asymmetry.} Non-agent configurations detect at
injection by construction, whereas agent configurations start the MTTR clock only when the monitoring
agent flags the fault (Section~\ref{sec:problem}). The agents' recovery times therefore omit a
detection interval that the non-agent figures include, which favors the agents in every MTTR
comparison. \emph{Cost measurement.} The metered term of Eq.~\eqref{eq:cost} is integrated between two
resource samples per run, which spans the 300\,s control loop for agent configurations but only a few
seconds for non-agent ones. In addition, the Airflow pool size and the streaming-worker target carry
over from one run to the next because the campaign never reset them. Cost comparisons therefore rest
mainly on the provisioning term, an assumption whose break-even point Section~\ref{sec:sensitivity}
reports, and the metered part should not be read as a like-for-like measurement.

\subsubsection{Scope of the Testbed}
The testbed is a single machine. The resource-contention scenario applies real CPU stress, which is
why runs cannot be parallelized and why the size of the campaign is bounded. The policy engine is
pinned to one release (Table~\ref{tab:testbed}), and lesson L6 (Section~\ref{sec:l6}) shows that a newer release from the
same vendor would have changed the adversarial result had the version not been pinned. We disclose
this as a property of our evaluation, not as a defect we investigated in the policy engine. Only four
fault types were injected, whereas a real pipeline's incident taxonomy is larger, and lesson L4
(Section~\ref{sec:l4}) shows that mapping an injected fault type onto a real incident type is not
automatic.

\subsubsection{Evidence Gaps}
Two components described in Section~\ref{sec:system} are implemented but not evaluated, and a third
gap lies within a contribution that is otherwise evaluated. \emph{Cross-model generalization.} The
harness that could test the base paper's claim of model independence is unit-tested, but its live
sweep against real provider models has not been run, so nothing here is evidence for or against that
claim. \emph{The trust core.} Graduated autonomy, the kill switch, and the blast-radius cap are
implemented and unit-tested, but every configuration ran in one fixed mode, so no mode transition or
kill-switch-to-halt latency was measured. \emph{Cost.} Internally the cost model of Eq.~\eqref{eq:cost} splits compute from
storage, but the per-run data we committed store only the total, and the metered term carries the
confound described above.

None of these gaps needs much more than a well-defined piece of additional work. For the cross-model
question, the sweep would be run on the same scenarios against at least two live providers, and the
trust core could be tested with a drill that engages the kill switch and a mode transition under load
while timing both. The cost problem is of a different kind, a flaw in our measurement rather than
missing evidence; it would be removed by a re-run in which the pool size and worker target are reset
before every run, resources are sampled at a fixed rate over the same window for all configurations,
and the component breakdown of the ledger is kept.

\subsubsection{What Would Change Our Conclusion}
The test we would most like to see is a repetition of the live-versus-mock comparison of
Section~\ref{sec:livemock} with a different provider. A gap of the same order of magnitude would
strengthen the central claim considerably; a much smaller one would point to a property of this
particular model pairing rather than of mock evaluation as such, and we would report that result in
the same way.

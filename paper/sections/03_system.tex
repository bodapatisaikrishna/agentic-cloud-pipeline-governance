\section{SYSTEM}\label{sec:system}

The system is organized in seven layers (Fig.~\ref{fig:arch}). Layers 1 and 2 form the data plane and
its telemetry, layer 3 holds the four bounded agents, layer 4 is the policy gate, and layer 5 executes
and audits whatever the gate allows. Layers 6 and 7, orchestration and enterprise governance, extend
the base paper's design. The campaign exercised layers 1 through 4, the write-ahead audit log in
layer 5, and the control loop and arbitration in layer 6. It did not exercise the autonomy-mode
transitions, did not engage the kill switch, and did not use layer 7. The remainder of this section
describes the layers in order.

\subsection{Layers 1 and 2: Data Plane and Telemetry}
A batch pipeline in Apache Airflow ingests a TPC-DS-derived dataset into versioned warehouse
partitions, and a streaming consumer reads from a Redpanda topic. All telemetry, including pipeline
metrics, resource usage, task runs, agent actions, failure events, and manual interventions, is
written to a PostgreSQL \texttt{telemetry} schema. Every experimental metric in this paper is
reconstructed from that schema rather than logged separately. The same layer tracks data freshness and
maintains the cost ledger behind the cost model of Eq.~\eqref{eq:cost}.

\subsection{Layers 3 and 6: Agents and Orchestration}
All four agents run the same loop. Each one \emph{observes} a telemetry snapshot, \emph{reasons}
about it with a live or mock language model, \emph{proposes} an action, and \emph{acts} only through
the gate. The monitoring agent is the
detector and is enabled in every agent configuration, so recovery time remains measurable in every
ablation. The optimization agent scales workers or pool slots, or reprioritizes work. The schema agent
accepts compatible schema changes and contains breaking ones. The recovery agent can retry, replay,
roll back, partially recompute, or hand the fault to a human. When two proposals target the same
resource, a static agent-priority bid resolves the conflict. An earlier design relied on lock ordering
for this purpose, but lock ordering turned out not to provide the property, so a per-target advisory
lock now serves only to stop a second process from acting on the same target.

\subsection{The Contract Between Layers 3 and 4}
An agent's only output is a \texttt{ProposedAction} with six fields: agent, action type, target,
parameters, justification, and confidence. A typed schema validates each proposal and rejects any
action type outside the agent's allowlist and any scaling target that is not an integer of at least
one. The second check was added after the adversarial corpus (Section~\ref{sec:results}) showed that
it was missing. Output that fails validation is rejected and logged, the
\texttt{agent\_output\_invalid} counter goes up, and that agent's turn becomes a \texttt{no\_action}.
Agents never emit or execute code.

\subsection{Layer 4: Policy Gate}
Each proposal carries a context built by the system: the projected marginal cost, the remaining
budget, the number of actions the proposing agent has taken in the last ten minutes, the schema
compatibility, and whether a prior version exists. The proposal then passes through four Rego policy
packs: the rate limit of Eq.~\eqref{eq:rate}, the cost budget of Eq.~\eqref{eq:budget}, a
recovery-approval policy that allows rollback only if a prior version exists, and a
schema-compatibility policy. The gate answers allow, deny, escalate, or allow-and-notify. When the
policy engine cannot be reached, the gate escalates; it never allows by default.

\subsection{Layer 5: Execution and Audit}
Before the executor starts, the system writes and commits an intent row. After the action, it updates
that row with the outcome. If the process crashes mid-action, what remains is a durable
\texttt{executing} row, not a missing record. The original design did not have this write-ahead
ordering; we added it later. Allowed actions reach their side effects through a dispatcher that picks
a handler by action type. On Airflow the handlers trigger DAG runs, clear tasks, and patch pool slots.
On PostgreSQL they perform rollback, quarantine, schema mapping, and desired-state updates.

\subsection{Simulated Human}
The on-call engineer is simulated. An escalation is resolved after a seeded log-normal delay (median
\NHumanMedian{}\,s, $\sigma=\NHumanSigma{}$). We chose this delay and did not measure it, and
Section~\ref{sec:sensitivity} shows how far the headline results move when it changes.

\subsection{Cross-Model Harness, Implemented but Not Evaluated}
The cross-model harness takes one scenario, runs it through a configurable list of LLM backends, and
scores each model on decision correctness (Eq.~\eqref{eq:decision}), latency, and token use. That is a direct test of the base
paper's model-independence claim. The harness has unit tests, but we did not run or record a sweep
across real provider models during this campaign, so this paper reports no results from it.

\subsection{Layers 5 and 6: Trust Core, Implemented but Not Evaluated}
The system also adds something the base paper does not have: a graduated-autonomy layer with three
modes. In \texttt{shadow} mode, proposals are logged and the pipeline is left alone. In
\texttt{approval} mode, allowed actions wait in a queue for a human to decide. In \texttt{autonomous}
mode they run directly. Two further limits act independently of the policy: a durable kill switch that
the loop checks once per tick, and an hourly blast-radius cap for each target. All three are
implemented and unit-tested. Every configuration in the campaign, however, stayed in
\texttt{autonomous} mode for the whole run, so we can describe what this layer does but not how it
performed.

\subsection{Layer 7: Enterprise Governance, Implemented but Not Evaluated}
An operator API provides read access to proposals, the audit trail, and costs, and it exports the
full audit log through a keyset cursor. Role-based access control with viewer, approver, and admin
roles, together with a tenant registry, binds each actor to a tenant and lets an operator suspend a
tenant. This layer supports multi-tenant deployment but played no part in the experimental
measurements.

\subsection{Cloud Deployment}
To show that the governance stack runs outside the laboratory host, we deployed it to a single
Microsoft Azure virtual machine (Fig.~\ref{fig:deploy}): a \texttt{Standard\_B2pls\_v2} instance
(Arm64, 2 vCPU, 4\,GB) running Ubuntu 24.04 in the Southeast Asia region. One script provisions the
machine, and cloud-init installs Docker, generates every secret on the machine itself, and starts a
Docker Compose stack of PostgreSQL, the policy engine, the operator API, and the control loop. Caddy
sits in front as a reverse proxy, gets a certificate from Let's Encrypt, and serves the API over
HTTPS. Ports 443 and 80 are open to the internet, while SSH is open only to the deployer's address.
The policy engine is the same pinned release used in the campaign, built for Arm64. There is no
production pipeline behind this deployment, so it runs in \texttt{shadow} mode with the mock model and
a no-op connector: it watches and proposes, and it never acts. We checked that the certificate is
valid, that HTTP redirects to HTTPS, that every protected endpoint asks for authentication, and that
all seven readiness checks pass. Nothing in Section~\ref{sec:results} was measured on this machine.
The campaign needs the full stack, including Airflow and Redpanda, which this deployment does not
run.

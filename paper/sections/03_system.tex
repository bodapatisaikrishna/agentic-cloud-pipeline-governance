\section{SYSTEM}\label{sec:system}

The system is organized in seven layers (Fig.~\ref{fig:arch}). Layers 1 and 2 form the data plane and
its telemetry, layer 3 holds the four bounded agents, layer 4 is the policy gate, and layer 5 executes
and audits whatever the gate allows. Layers 6 and 7, orchestration and enterprise governance, extend
the base paper's design. The campaign exercised layers 1 through 4, the write-ahead audit log in
layer 5, and the control loop and arbitration in layer 6. It did not exercise the autonomy-mode
transitions, did not engage the kill switch, and did not use layer 7. The remainder of this section
describes the layers in order.

\subsection{Layers 1 and 2: Data Plane and Telemetry}
A batch pipeline in Apache Airflow ingests a TPC-DS-derived dataset into versioned warehouse
partitions, and a streaming consumer reads from a Redpanda topic. All telemetry, including pipeline
metrics, resource usage, task runs, agent actions, failure events, and manual interventions, is
written to a PostgreSQL \texttt{telemetry} schema. Every experimental metric in this paper is
reconstructed from that schema rather than logged separately. The same layer tracks data freshness and
maintains the cost ledger behind the cost model of Eq.~\eqref{eq:cost}.

\subsection{Layers 3 and 6: Agents and Orchestration}
All four agents run the same loop. Each one \emph{observes} a telemetry snapshot, \emph{reasons}
about it with a live or mock language model, \emph{proposes} an action, and \emph{acts} only through
the gate. The monitoring agent is the
detector and is enabled in every agent configuration, so recovery time remains measurable in every
ablation. The optimization agent scales workers or pool slots, or reprioritizes work. Schema changes
that are compatible are accepted by the schema agent and breaking ones are contained, while the
recovery agent has a wider repertoire (retry, replay, rollback, partial recomputation) and can also
hand a fault over to the human. When two proposals target the same
resource, a static agent-priority bid resolves the conflict. An earlier design relied on lock ordering
for this purpose, but lock ordering turned out not to provide the property, so a per-target advisory
lock now serves only to stop a second process from acting on the same target.

\subsection{The Contract Between Layers 3 and 4}
An agent's only output is a \texttt{ProposedAction} with six fields: agent, action type, target,
parameters, justification, and confidence. A typed schema validates each proposal and rejects any
action type outside the agent's allowlist and any scaling target that is not an integer of at least
one. The second check was added after the adversarial corpus (Section~\ref{sec:results}) showed that
it was missing. Output that fails validation is rejected and logged, the
\texttt{agent\_output\_invalid} counter goes up, and that agent's turn becomes a \texttt{no\_action}.
Agents never emit or execute code.

\subsection{Layer 4: Policy Gate}
The context $c$ of Section~\ref{sec:problem} is assembled by the system, not by the agent, and is
attached to each proposal before it is evaluated by four Rego policy packs. Two of them are the rate
limit of Eq.~\eqref{eq:rate} and the cost budget of Eq.~\eqref{eq:budget}; the third approves a
rollback only when a prior version exists, and the fourth checks schema compatibility. Any of the four
verdicts (allow, deny, escalate, allow-and-notify) can come back, and if the policy engine is
unreachable the proposal is escalated, so nothing is ever allowed by default.

\subsection{Layer 5: Execution and Audit}
An intent row is written and committed before the executor starts and is updated with the outcome
once the action has finished, so a process that crashes halfway through leaves a durable
\texttt{executing} row behind instead of no record at all. This write-ahead ordering was not part
of the original design and was added later (lesson L2, Section~\ref{sec:l2}). Side effects are
produced by handlers that a dispatcher selects by action type; against Airflow these trigger DAG
runs, clear tasks or patch pool slots, and against PostgreSQL they carry out rollbacks, quarantines,
schema mappings and desired-state updates.

\subsection{Simulated Human}
No real engineer was on call. Escalations were resolved by a simulator after a seeded log-normal delay
with a median of \NHumanMedian{}\,s and $\sigma=\NHumanSigma{}$, values we picked rather than
measured; Section~\ref{sec:sensitivity} reports how much the headline results depend on them.

\subsection{Cross-Model Harness, Implemented but Not Evaluated}
Given one scenario and a configurable list of LLM backends, the cross-model harness runs the scenario
on each backend and records decision correctness (Eq.~\eqref{eq:decision}), latency and token use,
which would test the base paper's model-independence claim directly. It is covered by unit tests, but
no sweep over real provider models was run or recorded in this campaign, and the paper therefore
contains no results from it.

\subsection{Layers 5 and 6: Trust Core, Implemented but Not Evaluated}
Beyond the base design, our implementation has a graduated-autonomy layer. In \texttt{shadow} mode
proposals are only logged and the pipeline is not touched; in \texttt{approval} mode allowed actions
are queued until a human decides on them; and in \texttt{autonomous} mode they are executed
directly. Independently of the policy, the loop also checks a durable kill switch on every tick and
enforces an hourly blast-radius cap per target. These mechanisms are implemented and have unit
tests, but since every configuration in the campaign ran in \texttt{autonomous} mode throughout, we
can say what the layer does and not how well it works.

\subsection{Layer 7: Enterprise Governance, Implemented but Not Evaluated}
An operator API provides read access to proposals, the audit trail, and costs, and it exports the
full audit log through a keyset cursor. Role-based access control with viewer, approver, and admin
roles, together with a tenant registry, binds each actor to a tenant and lets an operator suspend a
tenant. This layer supports multi-tenant deployment but played no part in the experimental
measurements.

\subsection{Cloud Deployment}
To show that the governance stack runs outside the laboratory host, we deployed it to a single
Microsoft Azure virtual machine (Fig.~\ref{fig:deploy}): a \texttt{Standard\_B2pls\_v2} instance
(Arm64, 2 vCPU, 4\,GB) running Ubuntu 24.04 in the Southeast Asia region. One script provisions the
machine, and cloud-init installs Docker, generates every secret on the machine itself, and starts a
Docker Compose stack of PostgreSQL, the policy engine, the operator API, and the control loop. The API is served over HTTPS
by a Caddy reverse proxy with a Let's Encrypt certificate; ports 443 and 80 are reachable from the
internet and SSH only from the deployer's address. The policy engine runs the release pinned for the
campaign (Table~\ref{tab:testbed}), rebuilt for Arm64. Because no production pipeline sits behind
this machine, it runs in \texttt{shadow} mode with the mock model and a no-op connector, so it
observes and proposes but never acts. On the deployed instance we confirmed a valid certificate, the
HTTP-to-HTTPS redirect, authentication on every protected endpoint and a pass on all seven readiness
checks. None of the results in Section~\ref{sec:results} come from this machine, since the campaign
also needs Airflow and Redpanda and these are not part of the cloud deployment.

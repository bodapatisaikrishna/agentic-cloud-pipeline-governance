\section{EXPERIMENTAL DESIGN}\label{sec:method}

\subsection{Testbed}
Everything runs in containers on one node: PostgreSQL, Redpanda, Airflow, and OPA. Hardware, software
versions, and fixed parameters are listed in Table~\ref{tab:testbed}. The policy engine is pinned to a
single release, for reasons that become clear in Section~\ref{sec:results}. Runs never overlap. The
resource-contention scenario puts real load on the CPU, and a second run in parallel would add its own
load to the measurement.

\subsection{Scenarios and Configurations}
Four injected faults are crossed with eight configurations. The faults are schema drift (a column's
type changes), upstream delay, resource contention, and an ingress burst. The configurations are
\texttt{baseline} (static orchestration with the simulated human), \texttt{rule\_based}
(deterministic automation), \texttt{autoscale} (threshold autoscaling), \texttt{full} (all four
agents), and four ablations. Three ablations add exactly one agent to monitoring:
\texttt{recovery\_only}, \texttt{optimization\_only}, and \texttt{schema\_only}. The fourth,
\texttt{monitor\_only}, runs monitoring alone. None of the three non-agent configurations calls a
model.

\subsection{Non-Agent Baselines}
The three non-agent configurations model a responder's behavior rather than run a deployed
controller. In \texttt{baseline}, every fault escalates to the simulated on-call engineer. In
\texttt{rule\_based}, a fault covered by the rule set (upstream delay, resource contention, or ingress
burst) is resolved 30\,s after detection, while schema drift, which requires reasoning, escalates to
the human. In \texttt{autoscale}, the reactive scaler resolves resource contention and ingress bursts
20\,s after detection, and every data fault escalates. The recovery times of these configurations
therefore encode two assumed remediation latencies; they are not measurements of a real rule engine
or autoscaler. In that sense the comparators are idealized: their speed is whatever
latency we assumed, and since any fault outside their coverage still goes to the human, that latency
also bounds how well they can do overall.

\subsection{Matrix and Arms}
Pooled over the four scenarios, each baseline and \texttt{full} has $\NNBaseline{}$ runs; the
ablations have fewer, and the realized $n$ of every configuration is given in Table~\ref{tab:main}.
Since only the agent configurations ever call a model, the campaign was split into three arms that are
resumed independently and write to separate result directories, which rules out accidentally pooling
live and mock runs. The live model is used only in arm A, which holds the agent configurations. Arm B contains the non-agent
configurations with the model switched off; since they never call it, their results would be the
same under live and mock. Arm C runs \texttt{full} with a deterministic mock, as the direct
counterpart of \texttt{full} in arm A. The arms hold \NRunsArmA{}, \NRunsArmB{}, and \NRunsArmC{}
runs, \NRunsTotal{} altogether. Every run begins with a
120\,s warm-up before the fault is injected and ends with a 5\,s settle. Agent runs execute a 300\,s
control loop in between, whereas the non-agent responders resolve the fault without a loop.

\subsection{Live Model and Accounting}
The live arm calls a remote language model at temperature zero through an OpenAI-compatible endpoint.
The reasoning agents share one model, and monitoring uses a smaller, faster one. Model identifiers
are stored in each run's manifest, and a per-run budget caps the number of calls as well as the tokens
spent.

Two details of the accounting matter for validity. The first concerns caching: when a snapshot has
already been seen in the same run, its proposal is served from an in-run cache, and adding up the
per-action token columns would then count a single real call more than once. We therefore count real calls, cache hits, degraded proposals, invalid outputs,
tokens, and latency at the point where a call is made or skipped. A proposal is counted as degraded if
the budget has run out, if the provider is unavailable, or if it replays an earlier degradation.
Second, the project's pilot showed that caching a transient provider failure lets a single
rate-limit episode degrade every later identical snapshot (Section~\ref{sec:lessons}). Transient
failures are therefore no longer cached, and the degraded count is tracked separately.

\subsection{Metrics}
We report the five metrics defined in Section~\ref{sec:problem}: mean time to recovery (MTTR,
Eq.~\eqref{eq:mttr}), operational cost under a disclosed model (Eq.~\eqref{eq:cost}), manual
interventions, data freshness, and \emph{decision correctness} (Eq.~\eqref{eq:decision}). Every
configuration writes its manual interventions as rows of one shared telemetry table, which is where
they are counted, and freshness is read from the same telemetry as a lag in seconds.

\subsection{Seeds and Provenance}
The seed of each run is $\mathrm{sha256}(\texttt{config:scenario:replicate}) \bmod 2^{32}$. Because the
configuration name is part of the hash, two runs that share a (scenario, replicate) index but differ
in configuration draw different fault and human-latency randomness. They are matched in name only, so
the samples are treated as independent and the rank-sum test is the primary test, with the signed-rank
test on the matched index retained only for continuity with an earlier analysis. Each manifest line
stores the profile and model mode, the model identifiers (never credentials), the timings, the
human-latency and provisioning parameters, the budgets, and the code revision together with a flag for
uncommitted changes to the experiment code; runs whose provenance differs are not merged by the
analysis unless an explicit, documented override is supplied.

\subsection{Statistics}
We report medians with interquartile ranges, together with bootstrap 95\% intervals for medians and
for differences between medians. Each Cliff's $\delta$ is reported with its own bootstrap interval and
read against the conventional thresholds: $|\delta|<0.147$ negligible, $0.147$--$0.33$ small,
$0.33$--$0.474$ medium, and $\geq 0.474$ large~\cite{cliff1993}. Mann--Whitney $U$ tests are
Holm-corrected across the full family of comparisons, and proportions are given with Wilson
intervals. All comparisons in Section~\ref{sec:results} are exploratory. The campaign was designed and
run before any individual comparison was written up, and it was not pre-registered as a confirmatory
study.

\subsection{Adversarial Evaluation}
A generated corpus probes the policy layer directly. It covers every legal (agent, action) pair on an
exhaustive grid, crossed with the context values that drive decisions. Boundary cases are included,
for example 4, 5, and 6 recent actions, or a cost exactly at or just above the budget. The corpus also
has extreme parameter values chosen by an attacker and priced by the real gate, hostile strings in
free-text fields, illegal proposals sent straight to the policy engine so that they skip the
contract, and a seeded fuzz. Expected verdicts come from a separate Python implementation of the
\emph{documented} policy semantics, which shares no code with the Rego being tested. Both were written
by the same team, so the independence is in the code, not in the people. In line with the threat
model, the agent controls its own proposal and nothing else. The system builds the policy context, and
the agent cannot reach it.

\subsection{Sensitivity}
Each sampled human latency equals $\mathrm{median}\cdot e^{\sigma Z}$ with $Z$ fixed by the seed,
so within this scale family an outcome that the human handles alone scales exactly with the assumed
median. After confirming this linearity on the sampler, we used it to derive in closed form, for every
configuration, the human median below which that configuration stops beating the baseline. The cost
analysis is a sweep over the provisioning parameters, from which the break-even point is read.

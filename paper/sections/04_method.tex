is pinned to a specific release, and Section~\ref{sec:results} shows why the pin matters. Runs execute
strictly one at a time, because the resource-contention scenario applies real CPU stress and
concurrent runs would add host load to the measurement.

\subsection{Scenarios and Configurations}
Four injected faults are crossed with eight configurations. The faults are schema drift (a column's
type changes), upstream delay, resource contention, and an ingress burst. The configurations are
\texttt{baseline} (static orchestration with the simulated human), \texttt{rule\_based}
(deterministic automation), \texttt{autoscale} (threshold autoscaling), \texttt{full} (all four
agents), and four ablations. Three ablations add exactly one agent to monitoring:
\texttt{recovery\_only}, \texttt{optimization\_only}, and \texttt{schema\_only}. The fourth,
\texttt{monitor\_only}, runs monitoring alone. None of the three non-agent configurations calls a
model.

\subsection{Non-Agent Baselines}
The three non-agent configurations model a responder's behavior rather than run a deployed
controller. In \texttt{baseline}, every fault escalates to the simulated on-call engineer. In
\texttt{rule\_based}, a fault covered by the rule set (upstream delay, resource contention, or ingress
burst) is resolved 30\,s after detection, while schema drift, which requires reasoning, escalates to
the human. In \texttt{autoscale}, the reactive scaler resolves resource contention and ingress bursts
20\,s after detection, and every data fault escalates. The recovery times of these configurations
therefore encode two assumed remediation latencies; they are not measurements of a real rule engine
or autoscaler. They are idealized comparators: their speed follows from the assumed latencies, and any
fault outside their coverage still falls to the human, which bounds what they can achieve.

\subsection{Matrix and Arms}
The baselines and \texttt{full} each have $\NNBaseline{}$ runs pooled across the four scenarios, and
the ablations have fewer; Table~\ref{tab:main} gives the realized $n$ for each configuration. Because
only agent configurations call a model, the campaign is split into three independently resumable arms
with separate result directories, so live and mock conditions cannot be pooled by accident. Arm A
holds the live-model agent configurations. Arm B holds the non-agent configurations with the model
disabled; their results are identical under live and mock by construction. Arm C runs \texttt{full}
under a deterministic mock as the direct counterpart to arm A's \texttt{full}. The three arms contain
\NRunsArmA{}, \NRunsArmB{}, and \NRunsArmC{} runs, \NRunsTotal{} in total. Every run begins with a
120\,s warm-up before the fault is injected and ends with a 5\,s settle. Agent runs execute a 300\,s
control loop in between, whereas the non-agent responders resolve the fault without a loop.

\subsection{Live Model and Accounting}
The live arm calls a remote language model at temperature zero through an OpenAI-compatible endpoint.
The reasoning agents share one model, and monitoring uses a smaller, faster one. Model identifiers are
recorded in the run manifest, and a per-run budget caps model calls and tokens.

Two properties of the accounting matter for validity. First, a proposal for a snapshot that has
already been seen is served from an in-run cache, so summing per-action token columns would count one
real call several times. We therefore count real calls, cache hits, degraded proposals, invalid
outputs, tokens, and latency only at the moment a call is or is not actually made. A proposal counts
as degraded when the budget is exhausted, the provider is unavailable, or an earlier degradation is
replayed. Second, the project's pilot showed that caching a transient provider failure lets a single
rate-limit episode degrade every later identical snapshot (Section~\ref{sec:lessons}). Transient
failures are therefore no longer cached, and the degraded count is tracked separately.

\subsection{Metrics}
We report the five metrics defined in Section~\ref{sec:problem}: mean time to recovery (MTTR,
Eq.~\ref{eq:mttr}), operational cost under a disclosed model (Eq.~\ref{eq:cost}), manual
interventions, data freshness, and \emph{decision correctness} (Eq.~\ref{eq:decision}). Manual
interventions are a count of rows in a telemetry table that every configuration writes to, and
freshness is a lag in seconds read from the same telemetry.

\subsection{Seeds and Provenance}
The seed of each run is $\mathrm{sha256}(\texttt{config:scenario:replicate}) \bmod 2^{32}$. Because the
configuration name is part of the hash, runs matched on (scenario, replicate) share no fault or
human-latency randomness across configurations. The matching is therefore nominal rather than paired,
so we treat the samples as independent and use the rank-sum test as the primary test; the
signed-rank test on the matched index is kept only for continuity with earlier analysis. Each
manifest line records the profile, the model mode and identifiers (never credentials), the timings,
the human-latency and provisioning parameters, the budgets, the code revision, and whether the
experiment code had uncommitted changes. The analysis refuses to merge runs with differing provenance
unless an explicit, documented override is given.

\subsection{Statistics}
We report medians with interquartile ranges, together with bootstrap 95\% intervals for medians and
for differences between medians. Each Cliff's $\delta$ is reported with its own bootstrap interval and
read against the conventional thresholds: $|\delta|<0.147$ negligible, $0.147$--$0.33$ small,
$0.33$--$0.474$ medium, and $\geq 0.474$ large~\cite{cliff1993}. Mann--Whitney $U$ tests are
Holm-corrected across the full family of comparisons, and proportions are given with Wilson
intervals. All comparisons in Section~\ref{sec:results} are exploratory. The campaign was designed and
run before any individual comparison was written up, and it was not pre-registered as a confirmatory
study.

\subsection{Adversarial Evaluation}
A generated corpus probes the policy layer directly. It contains an exhaustive grid over every legal
(agent, action) pair and the decision-relevant context values, including boundary cases such as 4, 5,
and 6 recent actions and a cost equal to, or infinitesimally above, the budget. It also contains
attacker-controlled parameter extremes priced by the real gate, hostile strings in free-text fields,
illegal proposals sent directly to the policy engine without passing the contract, and a seeded fuzz.
The expected verdicts come from an independently written Python statement of the \emph{documented}
policy semantics that shares no code with the Rego under test. The independence lies in the
implementation, not in the authorship. Consistent with the threat model, the agent controls only its
own proposal, and the surrounding policy context is built by the system and lies outside the agent's
reach.

\subsection{Sensitivity}
Sampled human latency follows $\mathrm{median}\cdot e^{\sigma Z}$, with $Z$ fixed by the seed. In this
scale family any all-human outcome scales exactly linearly with the assumed median. We confirm the
linearity directly against the sampler and use it to derive, in closed form, the human median at
which each configuration stops outperforming the baseline. For the cost model, we sweep the
provisioning parameters and report where the break-even point lies.
